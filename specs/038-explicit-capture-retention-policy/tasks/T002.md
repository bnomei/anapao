## Context

Batch aggregation is not diagnostic retention. Add public
`AggregationConfig { schedule: CaptureSchedule, metrics: Selection<MetricKey> }` with
default/none/final-only/builders. Replace `BatchRunTemplate.capture` with `aggregation` and add
`with_aggregation` on template/config. Current canonical serialization writes `aggregation` only.
Legacy nested `capture` remains readable and maps only schedule/metrics; node, variable, and transfer
channels never had an observable `BatchReport` destination. Deprecated `with_capture` adapters may
remain for the `0.2` transition but must document that mapping.

Keep batch on the full `RunReport` execution path until after this task's baseline is saved. A
bounded internal adapter from aggregation schedule/metrics to the old full-report call is acceptable
only as sequencing scaffolding and must be removed by T003; do not expose it publicly or label
production APIs as tracer/prototype.

Freeze that adapter's baseline semantics: start from `CaptureConfig::default()` (so transfer
retention remains all), replace only schedule and metric selection from `AggregationConfig`, and run
the existing full-report batch path. For aggregation none, schedule suppresses step snapshots/series
but the old path still accumulates its historically discarded transfer log; this is the exact waste
the compact comparison must measure.

Land permanent measurement tooling before representation replacement:

- matched Criterion full/none/final/selective single-run targets;
- SingleThread/Rayon aggregation-all and aggregation-none batch targets;
- a custom `harness = false` `benches/capture_memory.rs` using dev-only `dhat = "0.3.3"`, one case
  per process,
  emitting JSON with total/max/current bytes and a consumed checksum;
- `scripts/bench-capture-memory save|compare --baseline NAME`, storing under `target/`, reporting
  absolute and relative deltas, and failing only for missing, invalid, or incomparable evidence—not
  for an unapproved improvement percentage.

Use existing `scripts/bench-criterion` for named default/parallel pre-change baselines. Patiently
wait for complete benchmark results. Record host, Rust version, features, case IDs, baseline names,
and consumed checksums in validation evidence. The existing non-failing 7% summary is an optional
descriptive view only and is not a spec pass/fail gate. Do not invent or silently change a threshold.

The fixed DHAT cases are `single_full_256`, `batch_none_256x256`, and `batch_all_256x256`.
For both batch cases, start from the deterministic source/sink fixture, replace its end condition
with 256 steps, and execute 256 runs in SingleThread mode. Use identical inputs before and after the
compact refactor.

## DoD

- Batch config has a separate aggregation type, complete builders/exports, and current/legacy nested
  Serde tests.
- All batch call sites compile against `aggregation`; active examples no longer suggest diagnostic
  capture controls batch-only outputs.
- Permanent Criterion and isolated DHAT cases are deterministic and consume results.
- `scripts/bench-capture-memory` save/compare interface is documented and machine-readable.
- Memory comparison reports absolute/relative deltas and rejects missing, invalid, or incomparable
  evidence without enforcing an improvement percentage.
- Pre-compact default Criterion, parallel Criterion, and peak-live-heap baselines are successfully
  saved before T003 changes execution representation.
- The full test/feature gate is green.
- A fresh Sol/high validator independently reviews nested Serde compatibility and benchmark validity
  before acceptance.

## Validation

```text
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-targets
cargo test --all-targets --features parallel
./scripts/bench-criterion save --bench simulation --baseline capture-retention-pre
./scripts/bench-criterion save --bench simulation --features parallel --baseline capture-retention-pre-parallel
./scripts/bench-capture-memory save --baseline capture-retention-pre
```

No Docker/service access is required. If `dhat` is not already cached, request approved network
access before the first dependency-resolving Cargo command. Benchmark commands are long-running and
must be allowed to finish rather than replaced with smoke-only runs.

## Escalate If

- A named pre-change baseline cannot be captured before compact-path edits begin.
- DHAT cannot isolate one case per process or report `max_bytes` without affecting library code.
- Nested legacy batch behavior cannot be mapped without ambiguity.
- The batch config change would require a public full-run retention destination.

## Notes

The baseline itself lives under `target/`; the benchmark target, script, and documentation are
durable repository artifacts.
